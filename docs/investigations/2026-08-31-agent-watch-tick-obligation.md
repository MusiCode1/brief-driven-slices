# מחקר: חובת־טיקים במעקב אחרי סוכנים (לבריפים / פקודות־משימה / autorun)

> **תאריך:** 2026-08-31 · **קהל:** כותבי פקודת־משימה, מתאמי `/autorun`, ומרדכי כשמשימה משגרת ילדים ארוכים.
>
> **השאלה:** מתי חייבים צופה־טיקים, מה חייב להיות בפרומפט של הטיק, ומה המתאם חייב לבדוק — כדי שלא יחליפו «חי» ב«עובד».
>
> **מקורות מדידה:** ריצות `cursor-sdk-acp` (30/08), TikTak 309, `acp-wire` / `acp-wire-http` / `acp-wire-be-dedupe` (31/08); עובדת basic-memory `צופה systemd ל-notify של drive-coding — PATH ו-CRLF`; `autonomous-runs/skills/autorun/SKILL.md` §מעקב־טיק.

---

## 1. למה זה רלוונטי לבריפים

בריף / פקודת־משימה שמניחים «נשגר ונחכה ל־notify» בלי צופה חיצוני **נכשלים בשקט**:

| הנחה בבריף | מה קורה בפועל |
|---|---|
| הילד יודיע בסוף (`notify_parent`) | אם נתקע באמצע — אפס הודעות; המתאם נרדם |
| `turnState` / `busy` מספיקים | חי ≠ עובד — idle/busy בלי git/דוחות/הודעות |
| לוג / HEARTBEAT לקובץ = ניטור | בלי `dispatch-via-api notify` הסוכן לא מתעורר |
| `nohup &` מתוך Shell של Cursor | מת אחרי טיק אחד |

**מסקנה לכותב המשימה:** אם יש שיגור ילד שצפוי >~5 דק׳ (מרדכי, אליעזר, או סוכן־עבודה ארוך) — **חובת־טיקים היא חלק מהצנרת**, לא אופציה. לא מספיק לכתוב בבריף «עקוב אחרי ההתקדמות».

---

## 2. החוזה התפעולי (מה חייב להתקיים)

### 2א. צופה חיצוני

- מרווח מוצהר: **~5 דק׳** (`INTERVAL_SEC=300`).
- הרצה: **tmux** או `systemd-run --user` — **לא** `nohup &` מתוך כלי־Shell של Cursor.
- כל טיק: `dispatch-via-api.mjs notify --agent <מתאם> --text "…"` (או לולאת Cursor tracked עם sentinel + אותו תוכן Action).
- **sleep אחד** לאיטרציה — sleep בראש ובסוף מכפיל את המרווח (נמדד: 10 דק׳ במקום 5).

### 2ב. פורמט ההודעה

```text
AGENT_WATCH_TICK <slice-or-task> #<n>/<max> @ <ISO-time>
<Worker|Mordechai>=<uuid> list=<status|busy|pid> turnState=<…> …
Action: <חובת תוכן — ראו §3>
```

בסיום משימה: `touch …DONE` / עצירת הלולאה + `session_close` לילדים שנפתחו.

### 2ג. מה אסור בפרומפט Action

| חלש / פסול | למה |
|---|---|
| `Action: session_state` בלבד | מעודד בדיקת חיות |
| `Action: בדוק אם חי` | בדיוק הכשל שנמדד |
| notify רק על DONE/ABORT | שקט כל עוד הריצה «חיה» |
| הסתמכות על `notify_on_output` כ־wake יחיד | לא מובטח (נמדד ב־309) |

## 3. חובת Action — חי ≠ עובד

**בכל טיק** המתאם חייב לבדוק **תוכן**, לא רק חיות. נוסח מינימום ל־`Action:`:

1. **הודעות / כלים אחרונים** של העובד (וילדים אם יש) — מה נעשה בפועל בדקות האחרונות (`session_state` + segments / tool calls).
2. **ארטיפקטים** — `git log`/`status` בעץ־ההרצה; ו/או דוחות `$BDS_REPORTS/…`; ו/או קבצי פלט ייעודיים למשימה (CSV, שיטסים, וכו׳).
3. **כלל תקיעה:** `idle`/`busy` בלי שינוי ב־(1)+(2) מאז הטיק הקודם ⇒ חזקת־תקיעה ⇒ דחיפה / שחזור / דיווח למשתמשת.
4. בסיום מוכח: `session_close` + עצירת הצופה.

זה אותו עיקרון כמו סנטינל־`.done` ב־`MISSION_TEMPLATE` (§הסנטינל הוא אות־חיות לא אות־סיום): **תהליך חי ≠ משימה מתקדמת**.

## 5. המלצות לכתיבת פקודת־משימה / בריף

כשהמשימה כוללת שיגור ילדים ארוכים, לכלול באילוצים / pre-flight:

1. **חובת צופה** — מי מרים (מתאם `/autorun`), מרווח 5 דק׳, tmux/systemd, `notify` בכל טיק.
2. **נוסח Action מלא** — להעתיק/להתאים מ־§3; לא «עקוב אחרי הסטטוס».
3. **מקורות אמת למשימה** — לציין במפורש מה נחשב התקדמות (קומיטים בעץ־הרצה, דוחות BDS, ארטיפקטי פלט).
4. **סגירה** — חובת־סוגר על כל id שנפתח; צופה נעצר עם DONE.
5. **הפניה** — למסמך זה + עובדת הצופה + `autorun/SKILL.md` §מעקב־טיק.

אין צורך לשכפל את כל מלכודות הצופה בתוך כל בריף — מספיק החובה + קישור למחקר/עובדה.
