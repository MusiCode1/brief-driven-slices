# שיגור סוכנים — MCP, ו-API לגיבוי

מקור האמת היחיד ל**איך משגרים** תפקיד BDS. שאר המסמכים מפנים לכאן ואינם מעתיקים פקודות.

> **אל תעתיק את המסמך הזה** לסוכן, לסקיל, או לפרויקט. הפניה + שער/notify קצרים במקום.

---

## הכלל

**אם בארגז-הכלים יש `session_open` — משגרים ב-MCP של drive-coding.**
**אם אין — `scripts/dispatch-via-api.mjs` מול אותו backend.**
אין מסלול שלישי.

הגילוי הוא מבט בארגז-הכלים, לא ניחוש ולא `ps`. כלי MCP שלא נענה (timeout, 404, `MCP_HTTP=0`) ⇒ נופלים ל-API **באותו תור**, לא ממציאים שיגור חדש.

שני המסלולים מדברים עם **אותו שרת**. אם ה-backend עצמו מת — שניהם נופלים.

---

## מי רץ על מה

| תפקיד | CLI + מודל |
|---|---|
| אליעזר, כלב (phase/light) | `cursor` · Composer 2.5 (מהרשימה אחרי `open`) |
| מרדכי, אביגיל, כלב-heavy | `claude` · Opus; נפילה → `cursor` · Grok |

"לא זמין" = `session_open` עם `cli: claude` נכשל, או אחרי פתיחה אין Opus ב-`configOptions`, או ה-`send` חוזר שגיאת מכסה/אימות. אז: סוגרים את הניסיון שנכשל, פותחים `cli: cursor`, ובוחרים Grok **מהרשימה**.


**אל תנחש מזהה-מודל בפתיחה.** נמדד 27/08: `modelOverride` בפתיחה נבלע בשקט, והסשן רץ על מודל אחר בלי שאיש ידע. רשימת המודלים נודעת **רק אחרי** שהסשן עלה.

`BDS_SLICE` חובה ב-`env` של כל שיגור לאליעזר/כלב. בלעדיו הילד מחזיר `WRONG-DISPATCH` ומסרב לבצע. עקיפה מודעת בלבד: המחרוזת `IN-PROCESS-APPROVED` בגוף הפרומפט.

## משגר — MCP

שיגור **לא חוסם**. `session_send` כברירת מחדל ממתין עד 1800ש' — זה תופס את השרשור הראשי והורג את ההורה בזרם-סרק (פער 6, ריצה 20). לכן **תמיד** `noWait: true`.

```
1. session_list                         — לא לפתוח כפיל לאותו cwd+cli
2. session_open
     cli, cwd (נתיב מוחלט),
     env: { BDS_SLICE: "<slice>" },
     permission: "allow_once"
   parent נגזר אוטומטית מכותרת X-Drive-Coding-Agent.
   אל תעביר parent במפורש אם הכותרת כבר מזהה אותך.
3. קרא configOptions מהתשובה. בחר מודל מהרשימה (טבלת התפקידים למעלה).
4. session_send
     agent, prompt,
     sets: { model: "<ערך מהרשימה>" },
     noWait: true
5. עקוב — אל תיעלם:
     notify_parent מהילד
     + session_state (האות הוא turnState, לא busy)
     + git log על ענף הסלייס
     + דוח ב-$BDS_REPORTS/<project>/
6. אחרי סיום מאומת + איסוף ראיה: session_close
```

`session_send` **אינו סוגר** את הסוכן. חובת-הסוגר היא שלך תמיד.

`session_close` מסרב כש-`turnState !== idle` אלא אם `force: true`. ב-`turnState` פתוח — אל תסגור; זה עדיין רץ. סגור **רק id שפתחת**.

## משגר — גיבוי API

אותו רצף, כשכלי MCP לא בארגז. `--no-wait` חובה מאותה סיבה.

```bash
# 1 · פתיחה. --parent רק אם יודע את המזהה שלך (DRIVE_CODING_AGENT_ID או session_list)
scripts/dispatch-via-api.mjs open --base http://127.0.0.1:<port> \
  --cli <claude|cursor> --cwd <worktree> --env BDS_SLICE=<סלייס> \
  --permission allow_once --json

# 2 · מודל מהרשימה שנדפסה, ואז משימה בלי המתנה
scripts/dispatch-via-api.mjs send --agent <id> --prompt-file <f> \
  --set "model=<ערך מהרשימה>" --no-wait

# 3 · אחרי איסוף ראיה
scripts/dispatch-via-api.mjs close --base http://127.0.0.1:<port> --agent <id>
```

אל תרים שרת על 4000/4001 — שם פריסות חיות. קוד-יציאה נמדד בלי צינור (`cmd | tail` מחזיר את הקוד של `tail`). משתני פריסה (`PORT`, `FE_STATIC_DIR`, `NODE_ENV`) דולפים לעץ-התהליכים — לנקות לפני מדידה.

### כשממתינים על `send` (רק אם שברת את כלל ה-noWait)

| קוד | משמעות | מה לעשות |
|---|---|---|
| 0 | הסתיים | הסקריפט סוגר לבד (בלי `--keep`) |
| 2 | פג-זמן | אינו כישלון — קרא שוב / `session_state` |
| 3 | הזרם נסגר בלבד | נמדד שהסוכן המשיך לעבוד. בדוק מצב; חי ⇒ התחבר מחדש, **אל תשגר המשך** |
| 5 | שקט, תקוע | אסוף ראיה, ואז `close` |

בכל קוד שאינו 0 הסוכן **נשאר חי במכוון** — הוא הראיה. אחרי האיסוף — אתה סוגר. בדוח-ריצה: שורת "סשנים שנפתחו ונסגרו". שורה ריקה שם היא חזקת-יתום.

האות הוא `turnState` מ-`/state` / `session_state`, **לא** `busy` מהרשימה. `busy` הוא debounce-שקט של 1.5ש' — סוכן שחושב מדווח `busy: false` באמצע תור.

## ילד — דיווח בסיום

השורה האחרונה לפני סיום, לא לפני. פעם אחת. ההודעה מצביעה על דוח — אינה מחליפה אותו. ילד שמת לא שולח כלום; לכן `notify` חוסך **המתנה**, לא **אימות**. הארטיפקט (`git log`, דוח ב-`$BDS_REPORTS`) הוא מקור האמת.

1. אם יש כלי `notify_parent` — קרא אותו.
2. אחרת אם `$DC_PARENT` מוגדר:

```bash
node "{{BDS_SCRIPTS}}/dispatch-via-api.mjs" \
  notify --base "$DC_BASE" --agent "$DC_PARENT" \
  --text "<תפקיד> סיים · <סלייס> · <verdict/קומיטים> · דוח: <נתיב>"
```

3. אחרת — דלג (אין כתובת-חזרה).

**אל תסגור את עצמך.** הסגירה היא של המשגר, אחרי שאסף.

`notify_parent` מופיע בארגז **רק** כשהסשן הזה הוא ילד (`parentAgentId`). סשן שורש לא יראה אותו — זה תקין.

## מעקב אחרי שיגור-רקע

אחרי שיגור אסור להיעלם. לא ממתינים על הזרם, לא קוראים את הטרנסקריפט של הצאצא.

🔴 **הצופה הוא `$BDS_SCRIPTS/watch-dispatch.sh` — חובה, אין צופה ad-hoc.**
שלוש ריצות רצופות (27–29) שילמו התערבות-צנרת על צופים מאולתרים (tg במקום
notify · נפילה אחרי WATCH_START · טיק-חי-בלי-בדיקת-עבודה). הסקריפט מגלם
את שלושתם: הכרעה לפי ארטיפקט, הערה ב-`notify` בלבד, גלאי-קיפאון.
פרטים: `OPEN-GAPS.md` פער 9.

```bash
tmux new-session -d -s <שם>-watch \
  "$BDS_SCRIPTS/watch-dispatch.sh <שם> --repo <P> --branch <B> --base <R> \
     --expect-commits <N> --notify-agent <המזהה-שלך>"
```

| מה בודקים | איך |
|---|---|
| הסלייס התחיל | `git worktree list` |
| התקדמות אמיתית | `git log --oneline <base>..<ענף>` |
| הילד חי / תקוע / סיים | `session_state` / `session_list` — `turnState` |
| שערים | `ls $BDS_REPORTS/<project>/` |
| דיווח מהילד | `notify_parent` (דחיפה לתוך תור רץ — נמדד 27/08) |

### 🔴 ‏`notify` ‏אינו מעיר משגר ש**‏סיים את התור** ‏— ‏נמדד 09/10/2026

‏"‏דחיפה לתוך תור **‏רץ**" ‏היא הניסוח המדויק, ‏ויש לו צד שני שעלה בריצה 68:
‏**‏למשגר שנכנס ל-`idle` ‏אין תור, ‏וה-notify ‏פשוט יושב.** ‏נמדד על סשן-בדיקה:

```
$ node dispatch-via-api.mjs notify --base http://127.0.0.1:4002 --agent <idle> --text …
‏✅ ‏נמסר · version=89          ← ‏rc=0, ‏ו-version עלה (‏ההודעה נרשמה)
# ‏ואחרי 40 ‏שניות:
turnState=idle                  ← ‏לא התחיל תור
```

🔑 **‏ומה שמפריד:** ‏סשן `attached:true` (‏CLI ‏מחובר) ‏**‏כן** ‏מתעורר — ‏הלקוח
‏המחובר מגלם הודעה-נכנסת כתור חדש. ‏סשן משוגר הוא `attached:false`,
‏`connectionCount:0`, ‏ולכן **‏אינו מתעורר מדיווחי ילדיו**.

‏⇒ **‏בשרשרת של 3+ ‏קומות (‏מתאם → ‏מרדכי → ‏אליעזר/כלב) ‏הקומה האמצעית
‏מתה לדיווחים.** ‏בריצה 68 ‏זה קרה **‏פעמיים**: ‏אליעזר סיים ו-27 ‏דקות אף
‏אחד לא ידע; ‏ואחר-כך הפריוויו הוקם והכתובת לא נמסרה.

**‏מה שעובד, ‏ולכן מה שעושים:**

| | |
|---|---|
| ‏🛑 ‏**‏לא** ‏לסמוך על `notify` ‏כאות-סיום בשרשרת עמוקה | ‏הוא נמסר, ‏מחזיר 0, ‏ולא קורה כלום |
| ‏✅ ‏`watch-dispatch.sh` ‏מכריע לפי **‏ארטיפקט** | ‏בדיוק הסיבה שהוא קיים |
| ‏✅ ‏`session_send` ‏**‏כן** ‏מתחיל תור בסוכן `idle` | ‏זו הדחיפה שמשחררת תקיעה |
| ‏✅ ‏הקומה שמשגיחה צריכה להיות `attached:true` | ‏או להחזיק צופה-ארטיפקט לכל קומה |

‏🛑 **‏ושתי מלכודות-צופה שנצרבו באותה ריצה:**
‏**‏(א)** ‏🔴 ‏**‏קיפאון-שווא לפני הקומיט הראשון הוא באג מוכר — ‏`docs/bugs/#2`**
‏(`TREE` ‏אינו מוקצה בסקריפט ⇒ ‏`progress_sig` ‏מודד את ה-checkout הראשי ולא את
‏ה-worktree). ‏**‏לקרוא אותו לפני שמסבירים תסמין כזה**, ‏ולא להמציא הסבר.
‏⚠️ ‏והוא **‏אינו מעוקב בגיט**, ‏כלומר אינו קיים למי שמשכפל את הריפו.

## מה לא לעשות

- ❌ `Task(subagent_type="eliezer"|"calev")` כמסלול-ריצה. זה מה שהשער `WRONG-DISPATCH` תופס.
- ❌ `session_send` בלי `noWait` / `send` בלי `--no-wait`.
- ❌ לנחש מודל ב-`session_open`.
- ❌ לסגור לפי גיל, לפי `cliKind`, או id שלא פתחת.
- ❌ להסיק סיום מ-`busy`, מקוד-יציאה של תהליך, או מהודעת `notify` לבדה.
- ❌ לשגר המשך כשהזרם נסגר והסוכן עדיין חי.
- ❌ לכתוב צופה ad-hoc (לולאת bash / systemd חד-פעמי) כשקיים `watch-dispatch.sh` — פער 9.
